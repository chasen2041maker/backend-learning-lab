# 对话学习日志：把真正讲通的知识长期保存下来

这里不是聊天记录备份，而是这个仓库最重要的“知识入口”之一。

平时主要通过对话、代码审查、报错和真实问题学习。一次讨论中如果真正纠正了一个长期会复用的理解，就整理成一份 learning journal；以后内容成熟，再合并进正式 lesson、cheatsheet 或 exercise。

---

## 什么值得记录

值得：

- 一个以前一直混淆的概念终于讲清楚；
- 纠正了一个错误心智模型；
- 某个真实故障让你理解了后端设计原因；
- 一次 code review 得到可推广的原则；
- 隔几周/几个月换电脑以后仍然值得回来查；
- 能用“为什么 + 失败场景”解释，而不只是记 API 名称。

例如：

```text
JWT ≠ Bearer Token
Bearer 是凭证使用方案
JWT 是 Token 格式
Cookie 是浏览器机制
Session 是服务端会话状态
```

这种非常适合记录。

---

## 什么不要记录

不要为了“完整”保存：

- 整段聊天原文；
- 问候/重复追问；
- 暂时没有证据的猜测；
- 一次网络抖动；
- 机器特定的临时输出；
- 大段 AI 生成但自己还没理解的内容；
- 已经在正式 lesson 里完整存在的重复说明。

目标是：

> **知识密度高，几个月以后还能读。**

---

## 一篇日志推荐结构

不必机械全部填写，但优先保留以下部分。

```markdown
# 日期 + 主题

## 为什么会问这个

当时混淆/问题是什么？

## 原来的理解

我原来以为……

## 纠正后的心智模型

用自己的话解释。

## 一条完整数据流

Client -> ... -> Database

## 最容易犯的错

至少一个实际失败场景。

## 和已有知识怎么连接

例如 JWT -> Middleware -> Principal -> tenant query。

## 我现在应该能回答

3～8 个关闭文档复述问题。

## 后续是否需要实验

如果只是阅读不够，链接到 exercise/TODO。
```

---

## 原理解一定要保留吗

如果它代表一个有价值的误区，建议保留。

例如：

```text
原理解：JWT Payload 看起来像乱码，所以是加密的。

纠正：常见 JWT Header/Payload 只是 Base64URL 编码；签名主要保护完整性，不自动保护机密性。
```

这种对比比只写正确答案更有复习价值，因为以后能提醒“我当时为什么会理解错”。

---

## 日志什么时候升级为 Lesson

当一个主题已经满足：

1. 不依赖当时聊天上下文也能看懂；
2. 有完整问题 -> 心智模型 -> 数据流 -> 失败模式；
3. 可以帮助其他初学者独立学习；
4. 有稳定结论，不是某个版本的临时 UI/命令；
5. 能链接实际实验或验证方法；

就可以把通用部分提升到 `lessons/`。

例如：

```text
2026-08-24-auth-jwt-session.md
↓
内容成熟
↓
lessons/10-auth-security.md
```

日志仍可以保留作为当时的学习轨迹，但避免两边大段重复。

---

## 什么时候做 Cheatsheet

如果一个主题已经理解，但隔几周容易忘关系，做速查：

```text
Cookie = 浏览器机制
Session = 服务端会话
Bearer = Token 使用方案
JWT = Token 格式
```

Cheatsheet 应该：

- 非常短；
- 强调关系；
- 不重新写完整教程。

---

## 什么时候新增 Exercise

当某个结论如果不亲手制造失败就很容易“假懂”，应该做实验。

例如：

```text
数据库 COMMIT 后响应丢失
```

光看描述容易觉得懂。

真正实验应该：

```text
INSERT + COMMIT
↓
return 前故意失败
↓
客户端重试
↓
观察是否重复创建
```

适合放进 `exercises/`。

---

## 文件命名

默认：

```text
YYYY-MM-DD-topic.md
```

例如：

```text
2026-08-24-auth-jwt-session.md
2026-09-02-go-context-deadline.md
2026-09-10-db-commit-retry.md
```

同一天同一主题不要拆很多碎片文件。

---

## 更新旧日志还是新建日志

如果只是继续同一个主题并补充成熟结论：

```text
更新旧日志
```

如果新的讨论核心问题已经不同：

```text
新建日志
```

例如：

```text
JWT 基础
```

和：

```text
OAuth Authorization Code + PKCE
```

虽然相关，但可以是两个独立主题。

---

## 对话中如何触发沉淀

可以直接说：

```text
这个知识点记进仓库
```

或者：

```text
把今天讲通的内容整理一下
```

或者使用约定的短触发词：

```text
更新仓库
```

`更新仓库` 的含义不是“把最近聊天全部保存”，而是：

```text
审当前对话
↓
找真正新增且长期有价值的知识
↓
先检查仓库是否已经覆盖
↓
决定更新 lesson / journal / cheatsheet / exercise
↓
没有新增价值时允许不制造空提交
↓
提交后验证远端 branch / compare / CI
```

维护时应该先检查仓库已有内容：

```text
已有 lesson 足够详细？
→ 只追加真正新的认知

已有内容太薄/有误？
→ 直接重构原文

只是一次值得保留的学习轨迹？
→ learning journal
```

不要每次都机械新增文件。

---

## 质量检查

一篇 learning journal 在提交前至少问：

- 删除聊天上下文后还能看懂吗？
- 有没有只写“是什么”，没写“为什么”？
- 有没有真实失败场景？
- 是否重复正式 lesson 大量内容？
- 是否包含公司/真实数据/Secret？
- 是否把临时产品 UI 当成长期后端知识？
- 关闭文档后是否有明确的复述目标？

---

这个目录最终应该像一条高密度学习轨迹：**不是记录问过多少问题，而是记录哪些心智模型真正被建立或纠正。**
