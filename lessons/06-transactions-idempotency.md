# 第 6 课：事务、并发更新和幂等

## 事务保护什么

事务保证一组数据库操作要么全部提交，要么全部回滚。例如：

```text
记录 Webhook 事件
更新工单状态
写入 Outbox 事件
```

三步应在同一事务中完成，否则可能出现工单更新了但通知永远没有生成。

## 事务不保护什么

数据库事务不能自动回滚已经发出的 HTTP 请求、邮件或消息。不要在持有数据库锁时调用一个可能等待 30 秒的外部模型。

## 丢失更新

两个请求同时读取 `version=1`，分别修改后都写回，会覆盖其中一个结果。

乐观锁：

```sql
UPDATE tickets
SET status = $1, version = version + 1
WHERE id = $2 AND tenant_id = $3 AND version = $4;
```

影响行数为 0，说明不存在或版本冲突。

悲观锁：

```sql
SELECT * FROM tickets
WHERE id = $1 AND tenant_id = $2
FOR UPDATE;
```

它会阻塞竞争事务，必须控制事务时长并按固定顺序加锁。

## 幂等 Webhook

可靠处理通常包含：

1. 验证签名和时间窗口；
2. 使用 `provider + event_id` 唯一约束去重；
3. 在事务中保存原始摘要、应用状态变化并写 Outbox；
4. 重复事件返回之前结果；
5. 只有本地持久化成功才返回成功；
6. 保留重放、审计和告警信息。

`webhook_security.py` 的 Processor 只用于观察失败重试与并发去重。生产实现不能用
进程内集合：必须用 PostgreSQL 的 `(provider, provider_event_id)` 唯一约束，并在同一事务中
写入 Webhook 状态、业务变更和 Outbox；只有该事务提交后，事件才是 `applied`。

## 三个失败窗口

1. **落库前宕机**：上游重试，事件尚未记录，可以重新处理；
2. **提交后响应前宕机**：上游重试，唯一约束识别重复并返回成功；
3. **状态更新后发通知前宕机**：同事务 Outbox 保证通知任务仍在库中等待发布。
