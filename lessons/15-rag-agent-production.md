# 第 15 课：把熟悉的 RAG/Agent 做成可靠服务

本课假设你已经理解 chunk、embedding、retrieval 和基本 RAG，不再重复入门定义。

## 从 Demo 到生产的差距

Demo 常见流程：

```text
问题 → 检索 → 拼 Prompt → 模型 → 答案
```

生产系统还需要：

- 可信用户与租户隔离；
- 文档 owner、版本、删除和权限过滤；
- 请求、Token、工具轮次、并发和成本预算；
- Provider health、超时、熔断和稳定降级；
- 来源、引用、结构化 Fact 和未知事实处理；
- 离线评测、Bad Case 分类、在线指标；
- Prompt 注入、敏感数据和输出安全；
- 任务取消、断线恢复和审计。

## Tool/Provider Registry

工具不应只写在 Prompt 文本中。Registry 保存：

- 名称、schema、权限、成本标签；
- Provider 健康状态；
- 超时和并发限制；
- 可用环境和功能开关。

Provider 不可用时，工具应从能力发现中消失或返回稳定错误，模型不能凭记忆补写事实。

## RAG 权限

必须先按用户/租户/资源权限过滤，再向模型提供内容。不要检索全库后要求模型“不要泄露”。删除文档时还要处理 chunk、embedding、缓存和搜索投影。

## 评测闭环

至少维护：

- 固定输入与期望事实；
- 检索 Recall@K / MRR 或任务相关指标；
- 引用是否真实存在；
- 必需事实覆盖率；
- 无资料时是否正确拒答；
- 延迟、Token、工具成功率和成本；
- Bad Case 根因标签，而不是只改 Prompt。

## 失败关闭和降级

- 金融、权限、额度等高风险事实缺失时明确失败；
- 非关键解释可以返回部分结果并披露缺失维度；
- 不把异常 JSON 静默“修补”为看似成功；
- 重试不能绕过预算和计费幂等。

## 练习

给你熟悉的 RAG 增加 `request_id`、tenant filter、检索 deadline、最大文档数、最大 Token、来源列表、无结果错误码和 20 条固定评测样本。
