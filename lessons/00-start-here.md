# 第 0 课：怎么把“听懂了”变成真正的后端能力

这不是要求你从头按顺序完成的第一章，而是这个仓库的使用说明。

你平时完全可以从一个真实问题开始，例如：

- JWT 到底是什么；
- goroutine 算并发还是并行；
- 为什么要 `go.mod`；
- 数据库提交成功但响应丢了怎么办；
- Docker image 为什么要存在；
- Session 和 JWT 到底差在哪。

问题本身可以跳跃，但学习过程要把新知识放回完整后端链路。

## 1. 后端不是一堆技术名词

以后遇到新名词，先把它放进这条数据流：

```text
客户端
  |
  | HTTP Request
  v
服务入口 / Router / Middleware
  |
  v
Handler
  |
  v
Service / 业务规则
  |
  v
Repository
  |
  v
Database

旁边可能还有：
Redis / Queue / Worker / 外部 API / Model
```

然后问：

1. 它在哪一层？
2. 它解决什么问题？
3. 不用它会怎样？
4. 它挂掉会怎样？

这四个问题比背 API 更重要。

## 2. 五级掌握标准

同一知识可以有完全不同的掌握程度。

### L1：见过

看到 `JWT`、`transaction`、`channel` 不陌生。

但只能说定义。

### L2：能解释

能自己画数据流，并说明：

- 输入从哪里来；
- 状态在哪里变化；
- 输出到哪里；
- 至少一个失败点。

例如不只是说：

> JWT 是 JSON Web Token。

而是能解释：

```text
登录
→ 服务端签发 Access Token
→ 客户端携带 Bearer Token
→ Middleware 验证
→ 产生可信 Principal
→ Handler 执行业务
```

### L3：能独立实现和排错

关闭答案以后，可以：

- 自己写最小实现；
- 写测试；
- 读错误；
- 找根因；
- 修复并验证。

### L4：能权衡

知道什么时候**不要**用它。

例如：

- Session 并不比 JWT “低级”；
- Redis 锁不是所有并发问题的答案；
- 微服务不是单体的升级版；
- K8s 不是所有项目的必需品。

### L5：能设计和审查

能把多个约束放在一起：安全、事务、并发、容量、恢复、观测、成本，并判断其他人的方案有什么风险。

这个仓库大部分基础内容追求 L2～L3；系统设计和工程取舍逐渐追求 L4。

## 3. 对话学习的正确闭环

推荐流程不是“先看 20 分钟教程，再做 40 分钟练习”，而是：

```text
真实问题 / 代码 / 报错
       ↓
先说出自己的理解
       ↓
纠正心智模型
       ↓
看一个最小例子
       ↓
亲手运行或修改
       ↓
故意制造一个失败
       ↓
解释为什么失败
       ↓
值得长期保留 -> 写入仓库
```

你可以直接问问题，不需要先把前面所有课程读完。

但如果某个问题依赖更底层知识，比如直接问“Redis 分布式锁为什么不安全”，却还没分清数据库事务和并发冲突，就应该暂时回到更底层补一块。

这就是 `LEARNING_ROADMAP.md` 的作用：**导航依赖，不控制时间。**

## 4. AI 应该帮什么，不应该替什么

AI 很适合：

- 用不同方式解释；
- 画数据流；
- 审查你的理解；
- 找代码风险；
- 给最小实验；
- 帮你比较方案；
- 把讲通的知识整理进仓库。

AI 不应该长期替你做：

- 还没尝试就生成整个功能；
- 你没看懂就直接合入大量代码；
- 用复杂框架隐藏底层问题；
- 用“最佳实践”代替具体失败场景。

如果你明确需要完整参考实现，可以要；但之后仍要能解释它为什么这样写。

## 5. 学代码时不要逐行背语法

优先按这个顺序：

```text
谁调用它？
↓
输入是什么？
↓
它改变了什么状态？
↓
返回什么？
↓
错误怎么传播？
↓
如果在这里宕机/超时/重复会怎样？
```

例如看到 Go Handler：

```go
func handler(w http.ResponseWriter, r *http.Request) {
    ...
}
```

先理解：

```text
HTTP Server
→ 根据路由找到 handler
→ r 表示请求
→ w 用来构造响应
```

之后再研究具体语法。

## 6. 每次只引入一个新的复杂度

错误学习方式：

```text
第一次做 API
同时上 Gin + GORM + PostgreSQL + Redis + JWT + Docker + Kafka
```

最后即使跑通，也不知道哪里在做什么。

更好的方式：

```text
内存 Handler
↓
分层
↓
数据库
↓
事务
↓
认证
↓
并发
↓
缓存
↓
异步
```

每加一步，都能比较“之前为什么不够”。

## 7. Debug 是学习的一部分

真正有价值的能力不是：

> 我第一次就写对。

而是：

```text
预期是什么
↓
实际是什么
↓
在哪里第一次变错
↓
什么假设能解释现象
↓
做哪个最小实验可以推翻/确认它
```

有代表性的真实问题记到 `progress/debug-log.md`。

## 8. 对话中讲通的知识怎么写进仓库

值得写：

- 一个长期容易混淆的概念终于讲清；
- 原来的理解被纠正；
- 一个失败场景改变了设计理解；
- 代码审查暴露了通用后端原则；
- 一段知识以后换电脑还会想回来查。

不值得写：

- 临时命令输出；
- 某次网络抖动；
- 重复问答；
- 没有确认的猜测；
- 整段聊天原文。

第一次通常放进 `notes/learning-journal/`，成熟以后再提升为正式 lesson。

## 9. 现在怎么开始

不要求执行一套“第一天任务”。

如果你正在写 Go，就从当前代码开始。

如果你正在理解认证，就读第 10 课。

如果你遇到 SQL，就读第 5～6 课。

如果不知道自己的问题在哪一层，打开：

- [后端能力路线](../LEARNING_ROADMAP.md)
- [知识地图](../notes/knowledge-map.md)

## 10. 最终判断

每学完一个知识，不要问：

> 我看完了吗？

问：

> 关闭这份文档以后，我能不能自己把它解释给另一个初学者？如果请求重复、两个请求同时来、数据库已经提交、依赖突然超时，我还能不能继续推演？

能做到，才是真正开始掌握。
