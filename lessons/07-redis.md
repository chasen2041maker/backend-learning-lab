# 第 7 课：Redis 是加速层和协调层，不是万能数据库

## 适合的场景

- 有 TTL 的缓存；
- 登录会话或短期验证码；
- 限流计数；
- 在线连接目录；
- Redis Streams 事件传递；
- 可丢失、可重建的派生状态。

## 不应只放 Redis 的事实

- 用户积分余额；
- 工单最终状态；
- 订单和支付状态；
- 审计记录；
- 无法从其他事实源重建的数据。

## Cache Aside

```text
读缓存
├─ 命中：返回
└─ 未命中：读 PostgreSQL → 写入带 TTL 的缓存 → 返回
```

写入常用“先更新数据库，再删除缓存”。即使如此仍要接受短暂不一致，并根据业务决定是否需要更强方案。

## 三类缓存风险

- 穿透：反复查询不存在的 Key；
- 击穿：一个热点 Key 到期，大量请求同时回源；
- 雪崩：大量 Key 同时到期或 Redis 故障。

应对包括负缓存、singleflight/锁、TTL 抖动、限流和降级，但不要无条件堆满所有机制。

## 分布式锁的边界

`SET key value NX PX` 只是起点。还要考虑：

- 锁过期后旧持有者继续执行；
- 释放时误删别人的锁；
- 长任务续租；
- 是否应该直接使用数据库唯一约束或 `FOR UPDATE`。

关键写入需要 fencing token 或事实库约束兜底。

## 练习

运行 Redis Lab：观察第一次回源、第二次命中、TTL 到期和缓存删除。然后解释 Redis 全部丢失时，系统怎样从 PostgreSQL 恢复。
