# 参考答案使用规则：答案是校准工具，不是学习起点

这个目录不会保存一套“把所有练习直接抄完”的最终成品。原因不是刻意为难，而是这个仓库的目标是建立：

```text
理解问题
→ 做最小尝试
→ 看失败证据
→ 修正心智模型
→ 再实现
```

如果第一步就复制完整答案，很多后端概念会变成“代码看起来熟悉”，但一换失败场景就不会判断。

## 什么时候可以看答案

不是固定“必须卡 30 分钟”。更合理的判断：

- 你已经能说清目标和当前失败；
- 至少做过一个有信息量的尝试/最小实验；
- 继续盲试只是在随机改代码；
- 或者你明确这一轮目标就是读 reference implementation，而不是独立挑战。

这时可以看提示或完整参考。

## 看答案的三个层级

### Level 1：只看方向

例如：

```text
这个规则属于 Service，不属于 Handler。
先检查 expected_version 的比较位置。
```

优先使用 exercise 的 `hints.md`。

### Level 2：看关键片段

只看你卡住的 5～20 行，不要把整个目录覆盖掉。

### Level 3：看完整 reference

可以看，但必须做两件事：

1. 逐段解释“为什么这样写、替代方案是什么”；
2. 关闭答案后从空白/旧版本重新实现关键部分。

## 当前仓库已有的参考

- SQL 的部分参考查询：`exercises/sql-postgres/reference-queries.sql`；
- Python/Go Ticket API：是可运行的**概念基线**，不是所有扩展任务答案；
- `reliability-labs/`：是故障语义演示，不是可复制到生产的框架；
- 综合项目没有最终大成品，因为每个 Phase 的“为什么引入”本身就是验收内容。

## 看完答案后怎么证明真正吸收

第二次不要照抄。至少完成其中两项：

- 从空白写回关键函数；
- 改一个条件并预测哪个测试会失败；
- 换一个输入/失败场景；
- 用另一种语言复现同一概念；
- 解释为什么某个常见替代写法会出 bug；
- 给实现补一个原答案没有覆盖的 regression/fault test。

## AI 给出的完整代码也属于“参考答案”

即使代码来自 ChatGPT/Codex，也要用同样标准：

```text
能运行
≠
我理解
≠
生产正确
```

合入学习仓库前至少知道：

```text
输入从哪里来？
状态在哪里变？
错误怎么传播？
事务/并发边界在哪里？
这里宕机会怎样？
测试证明了什么？
```

如果这些问题讲不清，先不要把“AI 生成且 tests green”当成能力完成。

## 提交学习成果时建议附带

```text
需求：
原始失败：
我的实现思路：
数据/请求流：
一个失败窗口：
验证命令：
结果：
仍未覆盖：
```

答案最大的价值，是帮你发现自己的心智模型哪里偏了；不是把 TODO 数量变成 0。
