# 二、截至目前真正已经讲通的 Repository / interface 内容

当前已建立的是下面这些内容。

## 1. `MemoryRepository` 实现 `Repository`

用户已经明确抓到本质：

> `MemoryRepository` 实现了 `Repository` interface。

Go 使用隐式实现：

```text
Repository interface 要求若干方法
↓
*MemoryRepository 拥有匹配的方法签名
↓
自动满足 Repository
```

不需要 `implements` 关键字。

## 2. Service 依赖 interface，而不是绑死具体实现

已讲：

```go
type Service struct {
    repository Repository
}
```

不是：

```go
repository *MemoryRepository
```

当前理解：

```text
Service 只关心 Repository 提供哪些能力
而不关心底层当前是不是 MemoryRepository
```

## 3. `s.repository.Get(...)` 为什么会进入 `MemoryRepository.Get(...)`

已讲 interface value 的第一轮运行时模型：

```text
Repository interface value
├─ 实际类型：*MemoryRepository
└─ 实际值：某个 MemoryRepository 对象
```

因此：

```go
s.repository.Get(...)
```

当前实际会分派到：

```text
(*MemoryRepository).Get(...)
```

用户已能连接：

```text
Handler
→ h.service.Get(...)
→ Service.Get(...)
→ s.repository.Get(...)
→ MemoryRepository.Get(...)
→ map
```

## 4. 小接口 / 消费者视角

已经做过第一轮解释：

```text
interface 应表达调用方真正需要的能力
而不是把具体实现所有方法全部塞进去
```

当前 Repository 包含 Create/Get/List/Update，是因为当前 Service 整体确实会使用这些行为。

## 5. Dependency Injection（DI）基础

已经讲通最基础模型：

```go
repository := NewMemoryRepository()
service := NewService(repository)
```

当前理解：

```text
Service 不自己创建并绑死 MemoryRepository
↓
外部先创建依赖
↓
通过 NewService(repository Repository) 传进去
```

同时已区分：

```text
启动阶段 = 组装 Repository / Service / Handler / Middleware
请求阶段 = 使用已经组装好的对象处理请求
```

到这里为止可以算 interface / DI 的 L2 初步对话理解。

# 三、Context 当前学习边界保持不变

2026-09-03 已经讲过：

```text
Client / Request 生命周期
→ r.Context()
→ Handler
→ Service
→ Repository
→ 支持 Context 的 DB/downstream API
```

以及：

```text
Request Context 的 cancel
= 由 net/http / Request 生命周期触发

WithCancel / WithTimeout 派生 Context 的 cancel()
= 创建派生 Context 的代码通常负责调用
```

已理解：

```text
父 Context cancel → 子 Context 一起结束
子 cancel → 不反向取消父
```

也已理解：

```text
Context 结束
≠ 强制杀死普通 Go 代码
```

