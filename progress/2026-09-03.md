# 1. Context 不是 HTTP 数据在层层重新传输

本次纠正了一个关键理解：

```text
Client 把 HTTP Request 发到 Go Server
↓
net/http 解析成 *http.Request
```

后面的：

```text
Handler → Service → Repository
```

不是 HTTP 字节重新通过网络传一遍，而是 Go 函数调用和参数传递。

`ctx` 也不是每层收到后再人工“通知下一层”。更准确的模型：

```text
Handler
Service
Repository
DB/downstream
```

都拿着同一条父子关联的请求生命周期信号链。

上游 Context 被取消后，下游已经关联的 Context 可以立即观察到结束状态；不需要：

```text
Handler 通知 Service
→ Service 再通知 Repository
→ Repository 再通知 DB
```

当前类比：

> Context 更像贯穿请求各层的一套报警线。上游一触发，接在线上的下游都能知道；但真正干活的代码仍必须愿意响应这个信号。

# 2. Context 结束与代码停止不是一回事

重要纠正：

```text
Context 已 canceled / deadline exceeded
≠ 普通 Go 代码被强制杀死
```

例如：

```go
time.Sleep(30 * time.Second)
```

不会因为 `ctx.Done()` 关闭而自动停止。

因此：

> **Context 发出“这项工作已经没有继续意义”的信号；真正的底层代码 / driver / API 必须支持并响应 Context，才能尽快停止。**

# 3. cancel 到底是谁触发

## Request Context

对于：

```go
r.Context()
```

当前理解：

```text
Client 断开 / Request 生命周期结束
↓
net/http 管理并取消 Request Context
↓
ctx.Done() 关闭
↓
ctx.Err() 可得到 context.Canceled 等原因
```

一般不是业务 Handler 自己去 `cancel(r.Context())`。

## 派生 Context

代码自己：

```go
ctx, cancel := context.WithTimeout(r.Context(), time.Second)
defer cancel()
```

当前理解：

```text
父 r.Context() 先取消
→ 子 ctx 跟着结束

子 timeout 到期
→ 子 ctx 自己 DeadlineExceeded

代码主动 cancel()
→ 子 ctx 主动 Canceled
```

同时：

```text
子 cancel
≠ 反向取消父 ctx
```

创建派生 Context 的代码通常负责 `defer cancel()`，即使 timeout 还没到，工作提前完成也应释放关联资源。

# 4. 为什么数据库正在工作时 Context 仍然有意义

提出的问题是：

> 如果 Repository 已经在查数据库，上层突然 cancel，数据库怎么办？

当前结论分两种。

## 支持 Context 的数据库调用

以后真实 Repository 会看到类似：

```go
db.QueryContext(ctx, query, ...)
db.ExecContext(ctx, query, ...)
```

目的之一就是把：

```text
Request cancel / deadline
```

传到真正耗资源的数据库工作，让 driver / DB 有机会取消当前查询并尽快返回 error。

完整方向：

```text
Client cancel
→ Request ctx canceled
→ Repository/DB call 观察 ctx
→ 尝试停止查询
→ error
→ Repository
→ Service
→ Handler
```

## 不支持 Context 的工作

如果底层只是：

```go
time.Sleep(...)
```

或使用完全不接受 Context 的阻塞 API，那么 Context 即使结束，这个工作仍可能继续。

所以：

```text
传 ctx 参数
≠ 自动拥有取消能力
```

真正的能力来自底层 API 对 Context 的支持。

# 5. COMMIT 后 cancel 不会回滚历史

本次顺带建立一个后续事务课程的重要边界：

```text
INSERT / UPDATE
↓
COMMIT 已成功
↓
Client 后来断开 / ctx cancel
```

不会自动把已经提交的数据库事实撤销。

因此未来还需要：

```text
Transaction
Idempotency
客户端超时重试
COMMIT 后 Response 前失败
```

来处理“客户端不知道到底成功没成功”的问题。

当前只记录这个边界，不提前展开。

# 6. `Repository interface` 与 `MemoryRepository`

当前已明确：

> **`MemoryRepository` 实现了 `Repository` interface。**

Go 是隐式实现，不需要：

```text
implements Repository
```

只要 `*MemoryRepository` 拥有 `Repository` 要求的全部方法且签名一致，就自动满足该接口。

当前仓库：

```text
Repository interface
要求：Create / Get / List / Update

*MemoryRepository
拥有：Create / Get / List / Update

因此：
*MemoryRepository satisfies Repository
```

# 7. Service 为什么依赖 Repository interface

真实结构：

```go
type Service struct {
    repository Repository
}
```

而不是：

```go
repository *MemoryRepository
```

当前理解：

> Service 不关心底层具体是 map、PostgreSQL 还是测试 Fake；它只要求“你能提供我需要的数据访问行为”。

所以未来可以：

```text
Service
↓ Repository interface
├─ MemoryRepository
├─ PostgresRepository
└─ FakeRepository
```

这样从 map 换到 PostgreSQL 时，业务层可以尽量不改。

# 8. interface value 里到底装什么

本次继续拆了：

```go
service := NewService(repository)
```

虽然 `NewService` 参数类型是：

```go
repository Repository
```

但 interface value 当前实际仍保存具体实现。

阅读模型：

```text
Repository interface value
├─ dynamic type  = *MemoryRepository
└─ dynamic value = 当前具体 MemoryRepository 对象
```

因此：

```go
s.repository.Get(...)
```

会根据 interface 中的实际具体类型，调用：

```text
(*MemoryRepository).Get(...)
```

如果以后注入：

```text
*PostgresRepository
```

同一行 `s.repository.Get(...)` 就会执行 PostgreSQL 实现。

这建立了 Go 中 interface + 隐式实现 + 动态分派的第一轮模型。

# 9. 小接口 / 消费者视角

本次建立：

> **接口优先表达“使用者真正需要什么能力”，不是把实现者所有方法全部列出来。**

例如一个消费者只需要 `Get`，理论上可以只依赖：

```go
type TicketGetter interface {
    Get(...)
}
```

这样测试 Fake 不需要为了满足一个巨型接口实现一堆根本不用的方法。

但同时做了修正：

```text
小接口 ≠ 越碎越高级
```

当前 `Service` 整体确实使用 `Create / Get / List / Update`，所以仓库现有 `Repository` interface 当前仍是合理合同。

# 10. Dependency Injection 已建立第一轮模型

当前代码：

```go
repository := NewMemoryRepository()
service := NewService(repository)
```

已经能读成：

```text
外部先创建 Repository 实现
↓
通过 NewService(repository Repository)
把依赖交给 Service
```

这就是最基础的：

```text
Dependency Injection
依赖注入
```

不是必须有 DI Framework 才叫依赖注入。

当前已经能区分：

```text
启动阶段
= 组装依赖 / Handler 链

请求阶段
= 使用已经组装好的 Service / Repository 处理请求
```

这也和之前 Middleware 的“启动时组装、请求时执行”重新连接起来。
