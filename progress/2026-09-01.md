# 1. `ctx` 是 context / 上下文，但不是“保证请求正常”

学习过程中形成的初始表达：

```text
ctx 是一种请求的生命线
```

这个类比保留，但做了精确修正：

```text
ctx 不保证请求一定成功 / 正常
ctx 负责携带并传播这次请求的生命周期状态
```

当前可以把它看作：

```text
ctx
├─ cancel：请求是否被取消
├─ deadline / timeout：还允许工作到什么时候
└─ 少量 request-scoped value：例如 Principal
```

业务参数仍显式传递，不把 Context 当万能参数袋。

---

# 2. `ctx` 最开始从 HTTP Request 来

真实 Handler：

```go
value, err := h.service.Create(
    r.Context(),
    principal.TenantID,
    input,
)
```

当前建立：

```text
Client 发 HTTP Request
↓
Go net/http 构造 *http.Request
↓
Request 自带 Context
↓
Handler 用 r.Context() 拿出来
```

因此 Service 的：

```go
func (s *Service) Create(ctx context.Context, ...)
```

里的 `ctx` 不是 Service 自己凭空创建的，而是 Handler 从这次 Request 传下来的。

---

# 3. 为什么 Handler → Service → Repository 一直传同一个请求关系

真实链：

```text
r.Context()
→ Handler
→ Service(ctx)
→ Repository(ctx)
```

核心原因：

> 如果上游请求已经取消或时间预算耗尽，下游真正干活的 Repository / DB / downstream 也应该有机会知道并停止。

错误做法的概念模型：

```go
s.repository.Get(context.Background(), ...)
```

这会把 Repository 从原 HTTP Request 的 cancel/deadline 传播链中切开。

当前已经理解：

```text
Client 已经不要结果
≠ 下游还应该无条件继续消耗资源
```

---

# 4. Authentication 为什么又创建了一个 ctx

真实代码：

```go
ctx := context.WithValue(r.Context(), principalContextKey{}, principal)
next.ServeHTTP(w, r.WithContext(ctx))
```

当前不是理解成“重新开一条完全无关的 Context”，而是：

```text
原 Request Context
├─ 生命周期关系
↓ 派生
新 Context
├─ 继续跟随原生命周期
└─ 加入 Principal
```

因此后续 Handler 可以：

```go
principalFromContext(r.Context())
```

拿到认证后的 Principal。

这也把之前学过的：

```text
Authorization Header
→ Authentication
→ Principal
```

重新接到真实 Request Context 上。

---

# 5. Context Value 不是业务参数仓库

本次明确区分：

```text
适合随 Context 传播：
request-scoped metadata，例如 Principal
```

而：

```text
title
ticketID
tenantID
expectedVersion
Ticket
```

这些是真正业务输入，应继续作为清晰的函数参数传递。

避免形成：

```text
什么都塞进 ctx
```

的误区。

# 6. `ctx.Err()`：问“Context 已经结束了吗，为什么？”

MemoryRepository 真实代码：

```go
if err := ctx.Err(); err != nil {
    return Ticket{}, err
}
```

本次补齐一个重要 Go 基础：

```text
nil
≈ Python None 的当前阅读类比
```

因此：

```text
err == nil
= 当前没有 error

err != nil
= 有 error
```

放到 Context：

```text
ctx.Err() == nil
= 当前没有因为 cancel/deadline 结束
```

生命周期结束时可能得到：

```text
context.Canceled
context.DeadlineExceeded
```

---

# 7. Context error 与业务 error 已分开

当前可以区分：

```text
ErrNotFound
ErrVersionConflict
= 业务 / 数据语义错误
```

和：

```text
context.Canceled
context.DeadlineExceeded
= 这次请求生命周期为什么结束
```

重要纠正：

> ctx 不是储存 Service / Repository 各种业务错误的地方。

`ctx.Err()` 关心的是 Context 生命周期结束原因。

---

# 8. Context error 仍走以前学过的返回链

如果 Repository 发现 ctx 已结束：

```text
Repository
→ return context.Canceled / DeadlineExceeded
↑
Service
→ 不继续业务逻辑，继续 return error
↑
Handler
→ 决定 HTTP 怎样表达
```

所以 Context 没有创造一套新的“神秘错误机制”。

它仍然连接到之前已经建立的：

```text
调用：Handler → Service → Repository
返回：Repository → Service → Handler
```

---

# 9. `ctx.Err()` 为什么不够：慢操作期间后来才 cancel

本次提出真实慢操作：

```text
0 秒：Repository 开始，ctx.Err() == nil
1 秒：开始慢操作
2 秒：Client cancel
3...10 秒：如果代码只在开头检查一次，就可能还在傻等
```

因此建立：

```text
ctx.Err()
= 现在主动检查一次
```

它不会自动把所有普通阻塞代码踢出去。

下游代码必须支持 / 响应 Context。

---

# 10. `ctx.Done()`：生命周期结束通知

当前最小理解：

```text
ctx.Err()
= 现在检查：结束了吗？为什么？

ctx.Done()
= 如果以后结束，通知我
```

对于慢操作，需要能够等待：

```text
工作完成
vs
Context 结束
```

概念性预览：

```go
select {
case <-workDone:
    // 工作完成
case <-ctx.Done():
    return ctx.Err()
}
```

当前只要求理解用途：

```text
ctx.Done()
→ 通知“结束了”

ctx.Err()
→ 告诉“为什么结束”
```

还没有要求掌握 channel / select 语法。

---

# 11. 当前关于 cancel / timeout 的最小模型

```text
Canceled
= 请求被取消

DeadlineExceeded
= 时间预算耗尽
```

共同含义：

```text
这次请求已经不应该继续正常工作
```

当前尚未展开：

```text
谁设置 timeout
deadline 怎样派生
cancel() 为什么要调用
Handler 最终映射什么 HTTP status
```

这些是下一自然小节。

# 12. 当前代码阅读能力新增

通过真实代码补齐：

```go
ctx context.Context
```

当前可读成：

```text
ctx
= 当前这次请求的 Context
```

以及：

```go
if err := ctx.Err(); err != nil {
    return Ticket{}, err
}
```

当前可顺着真实含义读：

```text
先检查这次请求生命周期是否已经结束
↓
若结束，把结束原因作为 error 返回
↓
若没结束，继续 Repository 工作
```
