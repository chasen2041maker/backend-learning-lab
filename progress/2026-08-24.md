## 今天的主线

今天围绕一条真实 HTTP 请求，开始把以前零散见过的后端名词串成一条完整的数据流。

示例请求：

```http
GET /api/v1/orders/123 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJ...
Accept: application/json
```

目标不是背名词，而是逐步理解：

```text
Client
→ DNS
→ IP + Port
→ TCP / TLS
→ OS / Socket
→ Go process
→ net/http
→ *http.Request
→ Router
→ Middleware
→ Authentication
→ Principal
→ Handler
→ Service
→ Repository
→ PostgreSQL
→ HTTP Response
→ Client
```

---

## 今天已经详细讲过的内容

### 1. 一条 HTTP Request 本身

开始能把请求拆开看，而不是把它当成一整串英文：

```text
GET
= HTTP Method，请求意图

/api/v1/orders/123
= Path，表示访问哪个 API/资源

123
= 常见 Path Parameter

HTTP/1.1
= HTTP 协议版本
```

还讲了：

- `Host` Header 的作用；
- Header 与 Body 的基本分工；
- `Authorization: Bearer ...` 如何连接到前面学过的 Token/JWT；
- `Accept` 表示希望服务端返回什么格式；
- `Content-Type` 表示当前发送的 Body 是什么格式；
- `GET` 请求通常为什么不需要 Body。

一个重要关系：

```text
Content-Type
= 我发给你的内容是什么格式

Accept
= 我希望你返回什么格式
```

---

### 2. Client 不等于“前端页面”

HTTP Client 可以是：

```text
Chrome / Edge
手机 App
curl
Postman
Python requests
Go http.Client
另一个后端服务
```

核心：

> Client 是主动向 Server 发请求的一方。

因此也再次连接到一个安全原则：

> 后端不能因为“前端不会这样传”就信任输入；调用者完全可以绕过前端直接请求 API。

---

### 3. Domain、DNS、IP、Port

今天开始建立：

```text
api.example.com
↓ DNS
203.0.113.10
↓
IP + Port
↓
找到具体网络服务
```

初步理解：

```text
IP
= 找到目标主机/网络接口

Port
= 找到这台主机上的具体网络服务
```

还连接了：

```text
127.0.0.1
= loopback / 本机回环地址
```

并强调：不同机器/容器里的 `127.0.0.1` 都表示“它自己”。

---

### 4. `connection refused` 为什么还没到 Handler

今天建立了一个很重要的排错层级：

如果目标 Port 没有进程监听：

```text
Client
→ IP + Port
→ 没有监听者
→ connection refused
```

此时通常还没有：

```text
*http.Request
Router
Middleware
Handler
Service
```

所以遇到 `connection refused` 时，不应该先去改 Handler。

---

### 5. TCP / TLS / HTTP 不是同一层

今天先建立到后端排错所需要的深度：

```text
HTTP
= 定义 Request / Response 的语义

TCP
= 常见情况下为应用提供可靠、有序的字节流

TLS
= HTTPS 中提供加密、完整性保护和服务器身份认证
```

一个重要连接：

> JWT 有签名，不等于可以不用 HTTPS。

因为 Bearer Token 一旦被直接偷走，攻击者可能不需要修改它就能重放。

---

### 6. 请求不是“网络直接调用 Go 函数”

今天把简化的：

```text
Network
→ Go Handler
```

展开成：

```text
Network
→ OS network stack
→ listening socket
→ Go process
→ net/http
→ parse HTTP bytes
→ *http.Request
```

因此开始理解：

```go
http.ListenAndServe(":8080", handler)
```

并不只是“运行 handler”，而是概念上包含：

```text
listen
→ accept connection
→ read HTTP bytes
→ parse request
→ build *http.Request
→ dispatch
```

---

### 7. `*http.Request` 与 `http.ResponseWriter`

开始把 Go 代码放回 HTTP 链路：

```go
func handler(w http.ResponseWriter, r *http.Request)
```

当前心智模型：

```text
r
= 这一次 HTTP Request 在 Go 中的对象表示

w
= Handler 用来构造 HTTP Response 的接口
```

例如网络中的：

```http
GET /orders/123
Authorization: Bearer xxx
```

进入 Go 后可以通过：

```go
r.Method
r.URL.Path
r.Header.Get("Authorization")
```

访问。

---

### 8. Router

今天明确了 Router 的核心职责：

```text
Method + Path
→ 找到对应 Handler
```

例如：

```text
GET /orders/{id}
→ getOrderHandler
```

还开始区分：

```text
404
= 没有匹配的路由/资源

405
= Path 有意义，但当前 Method 不允许
```

---

### 9. Middleware

今天不再只把 Middleware 记成“中间件”三个字，而是开始理解它为什么存在。

很多 Handler 都需要：

```text
Request ID
Logging
Authentication
Rate Limit
Recovery
```

如果每个 Handler 都复制，会重复且容易漏掉，所以形成：

```text
Request
→ Request-ID Middleware
→ Logging Middleware
→ Authentication Middleware
→ Handler
```

还讲了 wrapper / onion 模型：Middleware 可以在调用后续 Handler 前后都执行逻辑，因此 Logging Middleware 可以统计整个请求耗时。

---

### 10. Authentication -> Principal

把前面学过的 JWT 知识重新接回真实请求：

```text
Authorization: Bearer token
↓
Authentication Middleware
↓
验证 credential
↓
Principal(user / tenant / permissions)
```

最重要的信任边界：

```text
客户端 Body：user_id = 42
```

只是客户端声明，不可信。

而：

```text
Credential
→ 服务端验证
→ Principal.user_id = 42
```

才是服务端建立的可信身份上下文。

---

### 11. Authorization 不是永远只有一个 Middleware

今天纠正了一个容易形成的过度简化：

```text
Authentication
→ Authorization Middleware
→ Handler
```

只是教学图。

真实资源级权限有时需要先拿到资源才能判断，所以授权可能出现在：

```text
Middleware
Service
Repository query scope
owner / tenant boundary
```

核心不是记“授权在哪一层”，而是：

> 在拥有足够可信身份和资源上下文的位置，执行不可绕过的授权检查。

---

### 12. Handler / Service / Repository / Database

今天开始真正区分四层职责：

```text
Handler
= HTTP 世界与业务世界之间的适配层

Service
= 业务用例、业务规则

Repository
= 业务层访问持久化事实的边界

Database
= 存储和约束业务事实
```

特别纠正：

> Repository 不是“因为 SQL 太长，所以专门建一个放 SQL 的文件夹”。

它的价值是把业务规则与具体存储实现隔开。

---

### 13. tenant-scoped query

今天把认证/授权继续连接到 SQL：

```sql
SELECT ...
FROM orders
WHERE id = $1
  AND tenant_id = $2;
```

比：

```text
先按 id 随便查出来
→ 再在上层看看是不是当前 tenant
```

更能把租户边界压进数据访问路径。

---

### 14. 用“请求走到哪一层”排错

今天建立了一个非常重要的 Debug 方向：

> 遇到错误时，先判断请求最后确定成功经过了哪一层，以及第一个错误状态出现在哪里。

当前开始能按层理解：

```text
DNS failure
→ 域名解析阶段

connection refused
→ IP/Port 已找到，但网络监听阶段失败

TLS error
→ HTTPS 握手阶段

404 / 405
→ HTTP Server / Router 已经工作

400 / 422
→ 输入解析/验证附近

401
→ Authentication

403
→ Authorization

409
→ 业务状态/并发冲突常见

500 / 503
→ 服务内部或依赖失败
```

不要求死背状态码，重点是学会定位“请求到底走到哪里了”。
