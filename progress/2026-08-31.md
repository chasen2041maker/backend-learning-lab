# 1. Service 与 Repository 的职责边界进一步讲清

当前能用更直白的方式区分：

```text
Handler
= 接 HTTP、把 HTTP 输入翻译成业务调用

Service
= 当前业务用例的负责人；决定业务规则和状态怎么变化

Repository
= Service 需要读写数据时使用的数据访问边界
```

本次特别纠正了一个表述：

```text
不是 Repository 调真正的业务逻辑
而是 Service 组织业务逻辑，再调用 Repository 读写数据
```

通过 `Close Ticket` 流程进一步建立：

```text
Service.Close
→ 先 Get Ticket
→ 检查业务状态
→ 检查 version
→ open -> closed
→ version + 1
→ Repository.Update
```

因此开始理解：

> Service 不是“单纯中转层”，而是一个业务用例里组织步骤、执行规则、修改业务状态的地方。

# 5. 成功值和错误如何反向返回

通过 `Get` 已经建立：

```text
调用进去：
Handler
→ Service
→ Repository

return 回来：
Repository
→ Service
→ Handler
```

成功时：

```text
Repository return Ticket
→ Service return Ticket
→ Handler 转成 200 + JSON
```

失败时：

```text
Repository ErrNotFound
→ Service 往上返回
→ Handler 映射为 HTTP 404
```

因此开始理解 Go 中反复出现的：

```go
value, err := xxx()
if err != nil {
    return ..., err
}
```

本质是在做：下一层失败时，当前层先停止正常路径，把失败继续交给上层。

# 6. `Close Ticket` 让 Service 的业务职责变得具体

当前已顺过：

```text
Service.Close
↓
Service.Get
↓
Repository.Get
↓
拿回当前 Ticket
↓

↓

↓

↓

↓

当前重点理解：

= 把变化保存下来
```

这比只看 `Create` 时更清楚地证明了 Service 不是 HTTP helper，也不是 Repository 的简单转发器。

# 7. Version / 乐观并发控制建立第一轮理解

当前已讲：

```text
客户端/Service 手里认为自己在修改 Version 1
```

真正写入前 Repository 再看：

```text
current.Version == expectedVersion ?
```

如果：

```text
current.Version = 2
expectedVersion = 1
```

说明期间别人已经修改成功，当前请求持有旧状态，因此：

```text
→ ErrVersionConflict
→ 不允许旧数据覆盖新数据
```

已经理解为什么 Service 检查过一次 Version，Repository 写入前仍然需要检查：

```text
Service 检查
= 按当前读到的业务状态，这次操作是否合理

Repository 写前检查
= 真正落地这一刻，这个前提是否仍然成立
```

并开始接触术语：

```text
optimistic locking / optimistic concurrency
lost update
```

但目前只要求理解现象，不要求独立实现数据库级乐观锁。

# 8. `mutex` 与 Version 的区别

这是本次一个重要区分：

```text
mutex / RWMutex
= 保护当前 Go 进程里的共享内存 map，避免并发访问把内存操作搞乱

Version
= 保护业务数据，避免拿旧版本覆盖已经更新的新版本
```

已经理解：即使没有两个 goroutine 在同一瞬间访问 map，一个用户拿着旧 Version 隔一段时间回来保存，仍然可能发生业务冲突；所以 mutex 不能替代 Version。

也已经说明：以后换 PostgreSQL、多实例后，单个 Go 进程的 mutex 不能锁住别的服务进程，因此数据库并发控制需要由数据库更新条件/事务等机制承担。

# 9. `Lock / defer Unlock / RLock` 的 Go 阅读理解

已看真实：

```go
r.mu.Lock()
defer r.mu.Unlock()
```

当前理解：

```text
Lock
= 现在获取写锁

defer Unlock
= 先登记好：当前函数退出前一定执行 Unlock
```

这样即使中途：

```go
return Ticket{}, ErrNotFound
```

也不会忘记释放锁。

又看了：

```go
r.mu.RLock()
defer r.mu.RUnlock()
```

当前理解：

```text
RLock
= 读锁

多个读者可以并行读
写入需要独占
```

已建立最小模型：

```text
读 + 读
→ 可以一起

读 + 写
→ 需要互斥

写 + 写
→ 需要互斥
```

暂时不深入 `sync.RWMutex` 的底层实现。
