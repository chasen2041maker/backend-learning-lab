# Debug 问题日志：记录“怎么定位”，不是只记录“怎么修”

真正能迁移到下一次故障的能力，不是记住某个报错对应哪个命令，而是保留：

```text
现象
→ 证据
→ 假设
→ 最小实验
→ 第一个错误状态
→ 根因
→ 最小修复
→ 回归证据
```

每次至少记录一个真实问题。不要只写“修好了”。

## 推荐模板

```text
日期：
主题/功能：
相关文件：

【预期】
我原本期待发生什么：

【实际】
实际发生什么：
完整错误/HTTP 响应：
是否稳定复现：是/否

【复现】
最小复现步骤：
1.
2.
3.

【关联信息】
request_id：
trace_id：
event_id：
commit SHA：
环境差异：

【定位】
最后一个确定正确的状态：
第一个确定错误的状态：
我最初的假设：
支持这个假设的证据：
反对这个假设的证据：

【最小实验】
我只改变了什么：
如果结果是 A，说明：
如果结果是 B，说明：
实际结果：

【根因】
根因是什么：
为什么原测试/监控没提前发现：

【修复】
最小修复：
为什么没有顺便大重构：

【回归证据】
新增/修改测试：
验证命令：
修复前结果：
修复后结果：

【剩余风险】
仍未覆盖：
下一步是否值得做：
```

## 什么叫“第一个错误状态”

例如：

```text
客户端看到 500
```

500 只是最终症状。排查链可能是：

```text
HTTP request 正常
→ Handler input 正常
→ Service command 正常
→ Repository query 正常
→ DB UPDATE 返回 0 rows  ← 第一个异常
→ Service 错误分类错误
→ Handler 映射成 500
```

真正值得修的是第一个偏离预期的状态，而不是最后一层看到什么就改什么。

## 不要这样记录

```text
问题：接口不行
原因：代码 bug
解决：改了 if
```

这种记录以后几乎没有复用价值。

也不要一次列十个没有证据的可能原因。优先用最小实验快速排除。

## 一个高质量 Debug 记录至少证明三件事

1. 你能稳定复现；
2. 你有证据把根因和其他猜测区分开；
3. 修复后有 regression test 或等价自动验证，防止同类问题回来。

如果问题涉及并发、事务、缓存、异步消息或网络 timeout，再额外画出**时间顺序/失败窗口**，不要只画静态组件图。
