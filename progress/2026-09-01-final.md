# 1. 已讲 `WithTimeout` / `WithDeadline`

继续沿真实主线：

```text
HTTP Request
→ r.Context()
→ Handler
→ Service
→ Repository
```

建立：原始 `r.Context()` 不一定天然带业务所需的明确 deadline；拿到父 Context 的代码可以基于它派生更严格的子 Context。

概念代码：

```go
ctx, cancel := context.WithTimeout(parentCtx, 2*time.Second)
defer cancel()
```

当前理解：

```text
WithTimeout
= 基于父 ctx 派生一个“最多还能活多久”的子 ctx

WithDeadline
= 基于父 ctx 派生一个“最晚活到哪个时间点”的子 ctx
```

二者都保持父子生命周期关系：

```text
父 ctx 先取消
→ 子 ctx 一起结束

子 timeout/deadline 先到
→ 子 ctx 自己结束
```

不要把它理解成重新创建一条和 HTTP Request 无关的生命线。

---

# 2. `timeout` 和 `deadline` 的区别

当前最小模型：

```text
timeout
= 还能工作多久，例如 2 秒

deadline
= 最晚工作到哪个具体时间点
```

本质都在表达这项工作的时间预算。

---

# 3. `cancel()` 为什么仍然需要

即使使用 `WithTimeout`，工作也可能提前完成。

当前理解：

```text
cancel()
= 主动声明这个派生 Context 对应的工作已经不再需要继续
```

因此常见：

```go
ctx, cancel := context.WithTimeout(...)
defer cancel()
```

已把它和之前学过的：

```go
mu.Lock()
defer mu.Unlock()
```

连接起来：都是“创建/取得需要清理的资源后，提前登记函数退出时的清理动作”。

注意：当前只理解作用，还没有独立写 timeout 代码。

---

# 4. Slow Repository 模型已讲通

为了不脱离当前 Repository 主线，构造了：

```text
Repository 工作需要 3 秒
上游 timeout = 1 秒
```

先看错误模型：

```go
time.Sleep(3 * time.Second)
```

如果只在开始前调用一次：

```go
ctx.Err()
```

那么 1 秒后 Context 即使 timeout，普通 `Sleep` 也不会被 Context 魔法中断。

重要理解：

> **Context 不会强制杀掉普通函数；它负责发出结束信号，下游代码/API 必须愿意响应这个信号。**

---

# 5. 慢操作需要等待“工作完成 vs ctx.Done()”

概念预览：

```go
select {
case <-workDone:
    return value, nil
case <-ctx.Done():
    return Ticket{}, ctx.Err()
}
```

当前不要求掌握 channel / select 语法，只要求理解控制流：

```text
工作先完成
→ 正常返回

ctx 先结束
→ 立即停止等待
→ ctx.Err() 给出 Canceled / DeadlineExceeded
```

这也进一步巩固：

```text
ctx.Done()
= 结束通知

ctx.Err()
= 结束原因
```

---

# 6. Context error 继续走原有错误返回链

Slow Repository 如果因为 deadline 返回：

```text
context.DeadlineExceeded
```

仍然是：

```text
Repository
↑ error
Service
↑ error
Handler
```

Context 没有创造第二套错误系统。

当前教学代码的 Handler 尚未专门映射 Context error；不要提前死背 408 / 499 / 504，等 Error / Timeout 边界章节再讨论生产策略。

# 7. `context.Background()` 断链模型已经讲通

正确传播：

```text
HTTP Request ctx
↓
Handler
↓ ctx
Service
↓ ctx
Repository
```

错误示例：

```go
s.repository.Get(context.Background(), tenantID, id)
```

当前理解：

```text
context.Background()
= 一个独立根 Context 的最小阅读模型
```

如果 Service 丢掉上游 `ctx` 改用 `Background()`：

```text
HTTP Request cancel / deadline
↓
到 Service 为止
✂
Repository 收不到原请求生命周期结束信号
```

因此即使 Client 已经取消或超时，Repository 仍可能继续做无意义工作。

核心结论：

> **HTTP Request 链里的 Service 通常应该继续传播收到的 ctx，而不是无缘无故换成 `context.Background()`。**

---

# 8. `Background()` 不是“永远不能用”

当前只建立边界：

```text
属于某个 HTTP Request 的工作
→ 优先继承这个 Request 的 ctx

真正独立于 Request 的根任务 / 程序级初始化等
→ 才可能从 Background 等根 Context 开始
```

不要因为学了 Context 就把 `Background()` 绝对化为错误。

# 9. 当前 Context 能力证据

已经通过连续对话建立：

```text
r.Context() 从当前 HTTP Request 来
Handler → Service → Repository 传播同一请求关系
WithValue 派生 Context 并附加 Principal
业务参数不应全部塞 ctx
nil ≈ 当前可类比 Python None
ctx.Err()：检查是否结束以及原因
ctx.Done()：未来结束通知
Canceled / DeadlineExceeded：生命周期结束原因
WithTimeout / WithDeadline：对子工作增加时间边界
cancel()：主动结束派生 Context / 释放相关资源
Slow Repository：Context 不会强杀普通阻塞代码
context.Background()：会切断原 Request 的 cancel/deadline 传播
```
